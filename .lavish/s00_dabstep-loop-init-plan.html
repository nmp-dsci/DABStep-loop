One harness that runs a Claude agent over DABstep, scores it, versions it, and learns from every run

A new Python project downloads the Adyen DABstep benchmark, runs a Claude Agent SDK data-analysis agent over its 450 questions, scores answers with the benchmark's own scorer, tracks each run as a registered agent version, and writes the leaderboard submission. Phase 2 replicates NVIDIA's 1st-place recipe: learn on the ten labelled tasks with a strong model, distil a helper library, run inference with Haiku.

2 · Benchmark — 23 fee questions, permuted, decide the hard score

Every task is a factoid question over one fixed context folder. The 378 hard tasks are 23 core fee-calculation questions permuted over merchant, month and threshold, and all of them hinge on rules in manual.md plus matching logic over fees.json. That is why a plain ReAct agent scores about 20% hard and NVIDIA's helper library scores about 90%.

The scorer is lenient on numbers and strict on strings, so extraction matters more than prose

the five comparison steps, in order

  1. Lowercase and strip both sides.
  2. If either looks numeric with commas, compare numerically: both under 1 uses isclose(1e-4); otherwise round both to the fewer decimals of the two.
  3. Else if , or ; is present, split, strip brackets, sort, compare element-wise recursively.
  4. Else extract the first number from each and compare numerically if both parse.
  5. Else compare strings: exact after stripping non-word characters; a single word passes a subset test; otherwise SequenceMatcher.ratio() > 0.95.

3 · Labels — ten gold tasks are all anyone gets, so we learn NVIDIA's way

DABstep publishes exactly two task splits. Only the ten-row one has answers; the 450 answers live in a private adyen/DABstep-internal dataset that only the leaderboard reads. Your call in review: replicate how NVIDIA did it.

decided

What the protocol commits us to

  • Where does learning signal come from? One optimiser session per cycle sees the failed dev tasks with their gold answers and traces, and rewrites the system prompt and helper.py for the next version (§8).
  • How do the 450 teach anything without labels? Reflection: a strong model reviews traces for helper misuse and code mistakes, and checks group consistency across permutations of the same core question. Conflicts become prompt notes for the next version.
  • What is the official number? The leaderboard upload. Locally we report dev-10 accuracy plus label-free signals on the 450: answer-format validity, timeout rate, group-consistency rate, agreement between self-consistency passes.

What it rules out, and what it costs

  • Not done: no answer key is derived from the dataset's published task_scores files, though the data makes it possible. The submission notes can say "dev-10 only, NVIDIA-style".
  • The cost: ranking two prompts on ten tasks is noisy, so the phase-2 gate uses dev-10 pass/fail plus the consistency metrics, and each leaderboard upload is a manual form submit. Sonnet versus Haiku on v0 is measured by uploading both.
  • Room later: once the helper is verified, generating our own labelled question permutations is a clean add-on that touches no test data. Out of scope until asked.

04 · proposed architecture

4 · Architecture — one package, one CLI, five planes, files first

Everything a comparison needs is a file on disk first (predictions, scores, a run manifest) and a tracking-server record second, so the tracking backend stays replaceable. The highlighted path is v0's critical path.

The Agent SDK plus an in-process Python tool is the right v0 shape

  • Why the Agent SDK? You asked for it first, it gives Read/Grep/Glob for manual lookups free, and data-qa-agent and ConvFinQA already carry the exact ClaudeAgentOptions and ClaudeSDKClient call shape and env-sanitising rules to copy.
  • Why not just Bash? NVIDIA's decisive tool is a stateful Python executor (persistent namespace, pandas preloaded, REPL auto-print, timeout, repeat-code loop-breaker). Bash is stateless, so the executor is exposed as an in-process MCP tool and Bash stays off the v0 allow-list.
  • How does the answer come out? The system prompt demands a final {"agent_answer": …}; answer.py parses it, applies guideline hints, and falls back to "Not Applicable" on timeout. One session per task, a semaphore of 4 to start.

Versioning borrows the gate your other two projects already run

  • What is a version? A folder: agents/v0/ holds agent.yaml, system.md, optional helper.py and examples.md. Its fingerprint is the content hash plus the model id.
  • How is it registered? dabstep register mirrors each fingerprint into the MLflow model registry with the folder tarred as an artifact, so any past version can be checked out and re-run.
  • What passes the gate? dabstep compare A B: challenger's dev-10 score at or above champion's and no task flips pass to fail, plus no regression on the label-free 450 metrics. Different splits are refused as not comparable.
  • Where are models built? One module only; subscription_env() blanks ANTHROPIC_API_KEY and strips CLAUDE_CODE_* when billing is by subscription, so a run inside Claude Code never bills that session.

decided billing

Subscription in dev, never in prod, enforced in code rather than by care

  • How does dev bill? Through your Claude subscription via the CLI login. agent/llm.py is the only place a model is built; its subscription_env() blanks ANTHROPIC_API_KEY and strips every CLAUDE_CODE_* variable before spawning a session, the ConvFinQA rule, so a run started inside Claude Code never bills that session and never falls back to a key.
  • What if a key is present? The runner refuses to start with both a key and BILLING=subscription set, so which one paid is never ambiguous in a run manifest.
  • How does prod bill? It does not. The image carries DEMO_MODE=1 and no credentials of any kind; llm.py raises under demo mode; /ask replays a recorded pack. Nothing in App Runner can reach a model.
  • What replaces the cost metric? Input, output and cached tokens per task are still captured from the SDK's usage messages and logged to MLflow; the dollar figure is computed from the price table as an estimate and labelled as such. Plan limits are the cap: full 450 runs are sharded and resumable so a rate limit pauses rather than loses a run.

08 · the loop · settled in review

8 · The loop — one optimiser session, two surfaces, a ledger it must read first

This is the "optimisation loop on error" as you described it, confirmed: one Claude Agent SDK session sees every dev-10 failure with its trace, reads what earlier cycles tried and how they scored, diagnoses each failure, may change only the system prompt and the helper library, verifies each fix against the gold answer by running code, writes the next agent version, and records its diagnosis and proposals in a ledger. The harness then runs Haiku on the new version, gates it, and writes the outcome back into the same ledger entry so the next optimiser never repeats a change that did not work. NVIDIA's learn and distil stages collapse into this one session because it has the same tools they used across two.

Confirmed, with two refinements you should know about

  • One session? Yes. One ClaudeSDKClient session per cycle, Sonnet 5, up to 60 turns, with Read, Grep, Edit, Write and the same execute_python tool the agent uses, so it can reproduce a failure and test a fix in place.
  • Only the system prompt and helper.py? Yes, enforced: the session's Write and Edit tools are allowed only under agents/v(n+1)/, and a post-cycle check diffs the folder and rejects the version if anything but system.md and helper.py changed. Worked examples live inside system.md as a section rather than a third file, so "prompt" stays one surface. agent.yaml (model, turns, tools) is frozen for the loop; changing it is a human decision.
  • Does it make the new agent? Yes. Its output is the folder agents/v(n+1)/, fingerprinted and registered as @challenger. It never edits the champion in place, so a bad cycle costs nothing but tokens.
  • Refinement 1: the session must run the dev-10 regression tests and see them pass before it is allowed to end; a fix that breaks a passing task is caught inside the session, not by the gate.
  • Refinement 2: the gate is separate code, not the optimiser's opinion. Promotion needs the Haiku pass count to hold or rise and no task to flip pass to fail.

The ledger is how learning survives across cycles

loop/ledger.jsonl, one entry per cycle, committed. The optimiser's system prompt includes every prior entry, newest first, and instructs it to state for each diagnosis whether a similar change was tried before and what happened.

{"cycle": 3, "champion": "v2", "challenger": "v3",
 "failed": ["1273", "1681", "2697"],
 "diagnoses": [
   {"task_id": "1273",
    "symptom": "fee 0.10 vs gold 0.120132",
    "root_cause": "rules with is_credit=null excluded",
    "surface": "helper.py",
    "change": "matches_bool_field treats null as wildcard",
    "prior_attempts": [{"cycle": 1, "change": "prompt note on nulls", "outcome": "hold: 1273 still failed"}],
    "verified_in_session": true}],
 "prompt_diff_summary": "+ section: manual §5 null semantics",
 "helper_diff_summary": "+ matches_bool_field, ~ find_matching_fees",
 "outcome": {"verdict": "promote", "passes": "8 → 10",
             "fixed": ["1273", "1681", "2697"], "broken": []},
 "tokens": {"optimiser": 1.9e6, "eval": 1.4e6}}

The harness writes outcome after the gate; the optimiser writes everything else. prior_attempts is what stops it re-proposing a prompt note that already failed. The frontend's /loop page (§7) is a reader over this file, and MLflow gets the same entry as run tags so the two never disagree.

What make loop does, cycle by cycle, and when it stops

  1. eval the champion on dev-10 with Haiku; write the run folder; log it; list the failed task ids. If none, stop: dev-10 passes.
  2. Build the optimiser prompt: the ledger (all prior entries), each failed task with question, guidelines, gold answer, the agent's answer, and its full trace (tool calls, code, outputs).
  3. Run the optimiser session: diagnose per task, check prior attempts, edit system.md and helper.py under agents/v(n+1)/, verify each fix by running code, run the dev-10 regression tests, append the ledger entry.
  4. Reject the version if the folder diff touches anything else; register it as @challenger.
  5. eval the challenger on dev-10 with Haiku; compare against the champion; promote or hold; write the outcome, fixed and broken task ids into the ledger entry.
  6. Repeat from step 1 with the new champion, up to CYCLES (default 4) or until dev-10 is 10 of 10.

11 · risks & open questions

11 · Risks — each one has a mechanism in the plan, not a hope

Failure modes and the handling already designed in

  • DABstep-v2 lands mid-build? The data layer is one module keyed by dataset revision; splits and scorer version are in every run manifest, so v1 runs stay comparable and v2 becomes a new split.
  • Subprocess overhead and rate limits at 450 tasks? The runner resumes per task, retries transient failures, caps workers, and shards by task id.
  • Answer-format loss? answer.py is unit-tested against every guideline family: sorted lists, decimals, {scheme}:{fee}, "Not Applicable".
  • Sandbox safety? The Python tool runs in-process against a read-only symlinked workspace with no network; if Bash is ever enabled it gets NVIDIA's read-only allow-list.
  • Ten labels is a weak local signal? Mitigated by the label-free 450 metrics and by treating each leaderboard upload as the real measurement.
  • Autolog gaps? The CLI OTel export is the second source; both land in the same experiment.

Open questions beyond decisions B to D

  • Learning model for phase 2: Sonnet 5 (cheaper, likely enough) or Opus 5 (NVIDIA used Opus 4.5 and 4.6)? Default Sonnet 5; escalate if dev-10 traces are wrong.
  • Deploy prerequisites: the bootstrap Terraform (OIDC role) is run once by you with admin credentials before the first merge; confirm the region (ap-southeast-1, as ConvFinQA, because ap-southeast-2 is at the App Runner service cap).
  • Leaderboard identity: organisation and agent name for the form (must match ^[a-zA-Z0-9 _.-]+$).
  • Sonnet effort: compare medium and high as a run parameter, not a prompt change.
